Honest verdict (read this)

  
Two independent walls block the "brand-new hiker, just a browser, deep offline" story — and neither is a bug you can code around:

  
    
    
  1. No browser-created network. A browser cannot start a hotspot, cannot use Wi-Fi Direct, cannot open a listening socket. WebRTC here uses iceServers: [] (host candidates only) and connects fine — but only if the two phones already share an L2 network. Someone must enable an OS-level Personal Hotspot (a manual Settings step, no internet needed) and the other must join it. That step is outside the browser. Web Bluetooth is GATT-client only (a browser can't be a peripheral), Web Serial is wired, Web NFC is a few hundred bytes — there is no browser-accessible peer radio that works without a pre-shared network.
    2. 
    
  2. No browser-served origin to bootstrap the receiver. Cache Storage and Service Workers are origin-scoped and require isSecureContext (https or localhost). To end up with a runnable, installable PWA the receiver's page must already be running on https://hawktalk.ai/pwademo. Offline, a never-visited receiver cannot load that origin, and no browser API lets a peer mint it locally: a received bundle opened as file:// cannot register a SW, and a peer served over http://192.168.x.x is not a secure context either.
    3. 
  

  
What IS real (and prototyped here): the QR→WebRTC handshake, the DataChannel stream with backpressure, and reconstruction into Cache Storage + SW registration — when the receiver is already on the origin (installed shell, or localhost). That makes a genuinely useful narrower product: offline peer top-up — a hiker who has the shell but not the 131 MB model (or has a stale version) receives it from a peer with zero internet. "Viral to a stranger with a blank browser" is blocked.

  
iOS specifics: Safari does WebRTC DataChannels, Cache Storage, and Service Workers, and A2HS works — but (a) getUserMedia/SW need https, (b) storage for an origin can be evicted after ~7 days of non-use, which can silently delete a 131 MB received model between hikes, and (c) per-origin quota prompts can appear around a 131 MB write.

  
Bottom line: Path B's data plane (WebRTC + QR + cache reconstruction) is viable and built. Path B's "outside civilization, stranger, browser-only" premise is not, because the browser can neither create the link nor bootstrap the origin. A native seeder (Path A) that runs the hotspot AND serves the origin over a trusted-cert https local server is what would create the link Path B's WebRTC then rides.
